# v0.14 — Sources: one file, many names, many homes

Design for killing the repo-internal alias symlink workaround. Today a file
that must appear at several target paths under several names — the AGENTS.md
hub fan-in — is expressed as repo-internal symlinks (`agents/rules.md →
AGENTS.md`, `pi/AGENTS.md → ../agents/AGENTS.md`) so that each store has a
same-named file to link. Three separate stitch rules force this:

1. **1:1 name mapping.** A file links under its own name; a target that wants
   `rules.md` needs a repo file literally named `rules.md`.
2. **One store per target directory.** The store owning `~/.pi/agent` cannot
   be the agents fan-in store, so the agents file there must be "the pi
   store's file" — hence the alias inside `pi/`.
3. **No nesting within a store.** Even ignoring (2), `~/.config` and
   `~/.config/kilo` cannot both be targets of one store.

The aliases survive the stale-link sweep only by geometry: the sweep's
narrow ownership check (`points_into(store_dir)`) never matches a link that
resolves into *another* store's directory, and since 0.12.0 the sweep prunes
the repo subtree outright. That is protection by coincidence, not by design.

Source: the dots repo layout review on 2026-08-20, after shipping 0.13.0.
State: **approved** — this is the stitch driver's own layout; the workaround
exists to paper over a missing primitive, and this adds it.

---

## 0. Headline: file entries gain a decoupled source

One new state concept. A file entry stops being "a name that means both a
repo path and a target path" and becomes an explicit **target name → repo
source** mapping when the two differ:

```toml
[stores.pi]
target = "~/.pi/agent"
files = ["SYSTEM.md", "delegate.json", "keybindings.json", "models.json", "settings.json"]

[stores.pi.sources]
"AGENTS.md" = "agents/AGENTS.md"

[stores.agents.targets.kilocode]
target = "~/.kilocode/rules"

[stores.agents.targets.kilocode.sources]
"rules.md" = "agents/AGENTS.md"
```

`files` is unchanged sugar: `files = ["AGENTS.md"]` means the implicit
source `<store-dir>/AGENTS.md`. `sources` entries are the only way to say
"this target path's content lives elsewhere in the repo." The hub fan-in
becomes seven plain declarations around one real file, and every alias
symlink in the dots repo gets trashed.

Everything else in this plan is the consequence list: link lifecycle, sweep
ownership, add/remove semantics, import re-derivation, doctor checks, agent
JSON, and the migration of the one repo that uses the workaround (mine).

Red lines from AGENTS.md are unchanged and upheld. §5 adds a new one:
**remove never destroys a source another store still references.**

## 1. The primitive

### State shape

`GeneratedStore` and `GeneratedTarget` (src/config/types.rs) each gain:

```rust
#[serde(default, skip_serializing_if = "BTreeMap::is_empty")]
pub sources: BTreeMap<String, String>, // target rel path -> repo-relative source
```

Serialization order: `files`, `patterns`, then `[stores.<name>.sources]` as a
sub-table — generated TOML, machine-written, stable ordering by BTreeMap.

### Resolution model

`LinkTargets::Files(Vec<String>)` (src/store/resolve.rs) becomes
`Files(Vec<FileLink>)` where

```rust
pub struct FileLink {
    pub name: String,    // relative path in the target directory
    pub source: PathBuf, // absolute path in the repo
}
```

`resolve_target_names` builds `FileLink`s from `files` (source =
`store_dir.join(name)`) and `sources` (source = `repo_root.join(value)`),
sorted by name. Every consumer that today does `store_dir.join(name)` gets
the source from the `FileLink` instead. `name` still drives: target link
path, keep-set membership in the sweep, diff identity, report fields.

### Validation (load-time, load.rs — errors, not warnings)

- Source must not escape the repo root (after normalization, no `..`).
- Source must not live under `.stitch/`.
- Source must not itself be a symlink. **One hop only.** The feature exists
  to delete repo-internal indirection; chained sources would rebuild it in
  state form, with worse debugging (you'd need stitch to trace the chain
  instead of `ls -l`).
- A `sources` key must not also appear in `files` (ambiguity about which
  source wins) — error.
- A `sources` key must not collide with a pattern-produced name — error at
  resolve time, where pattern expansion happens.
- `sources` on a whole-dir store/target is an error. Whole-dir mode is a
  single directory link; per-file mapping is meaningless there.

### Decisions resolved (formerly open questions)

- **Repo-root-relative source paths**, not store-relative. Unambiguous, no
  traversal questions, reads correctly for cross-store refs
  (`agents/AGENTS.md`, not `../agents/AGENTS.md` mirroring the symlink we
  are deleting).
- **Sources may point into another store's directory.** That is the hub
  pattern. They may also point at non-store repo paths (a `shared/` dir) —
  no ownership requirement. A source is just a repo file.
- **Do NOT relax one-store-per-directory.** Considered path-level
  exclusivity (two stores, same dir, disjoint files). Rejected: it multiplies
  sweep-ownership and doctor-conflict cases and buys nothing once sources
  exist — the store that owns the dir declares a source, done. Directory
  exclusivity stays the invariant that makes sweeps safe.
- **Do NOT lift the no-nested-targets rule.** Still unneeded; same
  blast-radius argument.
- **Two names may share one source within a store.** Legal, harmless, no
  special-casing.
- **`sources` keys bypass `ignore`.** `ignore` filters glob expansion; an
  exact declaration beats a pattern.

## 2. Link lifecycle (apply / diff / templates)

- `create_link(target, FileLink.source)` — the linker already takes explicit
  paths; only the call sites change. `SourceMissing` now fires for missing
  out-of-store sources too, with the repo-relative path in the error.
- **Templates:** a source containing `{{ }}` renders into *this store's*
  staging (`.stitch/staging/<store>/<name>`), same as in-store sources —
  content is read from `FileLink.source`, written under the store's staging
  identity. Two stores may render the same template source differently when
  their hooks differ; that is correct, because staging is per-consumer. The
  final link points at the consumer's staging path, never at another store's.
- `diff` compares target link against `FileLink.source` (or staging path for
  rendered sources) — identity is per-consumer, so a shared plain source
  shows N healthy links, and a shared template shows N independent renders.
- Staging cleanup (`remove_empty_staging_parents`) is untouched: staging
  stays per-store, inside the repo.

## 3. Sweep, scan, prune, import

### Sweep (`reconcile_store_links`, src/render.rs)

Two changes, both to the *narrow* ownership check:

1. The keep-set comparison is by target rel path — already correct, untouched.
2. `points_into(path, store_dir) || points_into(path, &staging_dir)` gains
   the store's declared sources: a link whose rel path is *not* in the keep
   set but resolves to one of this store's declared source files is a
   **renamed-away or repointed** entry — treat as stale, exactly as an
   in-store stale link. A link resolving into another store's dir (and not
   one of ours) stays skipped, as today.

Net effect: ownership follows the manifest, not directory geometry. The
protection stops being a coincidence of where files live.

### Scan / prune (src/scan.rs)

Scan resolves link targets into repo paths and matches them against state.
It must match `FileLink.source` paths, not just store-dir prefixes, so a
healthy virtual link (`~/.pi/agent/AGENTS.md → repo agents/AGENTS.md`) is
recognized as covered by the pi store — and after it's removed from state,
prune lists it as stale instead of silently assuming another store owns it.

### Import (src/commands/import.rs)

Importing links that point into the repo must attribute them to the store
owning the **target directory**, with a `sources` entry — not fabricate a
store around a source path outside the store dir. The 0.12 fan-in work
(stow-style one-store-many-parents) already names targets per parent; the
source attribution is the remaining half. An imported link whose source
resolves into another store's dir yields `sources` on the target-dir owner.

## 4. add / remove

### add

- `stitch add <target-path> --source <repo-relative>`: register the target
  path with an explicit source — the fan-in flow. No file is moved or
  copied; the target path must be absent or already a link into the repo
  (else conflict, per existing rules — sources never override the
  foreign-content red line).
- `stitch add` on a path that is **already a symlink into the repo**
  (the manual `ln -s` flow): register as a `sources` entry pointing at the
  link's resolution. Today this is the adopt-a-link case that predates
  sources; with sources it becomes a first-class no-copy adoption.

### remove — the new red line

`remove <store>` when another store's `sources` references a file inside
this store's dir:

- Default: **refuse** with an error listing referencing stores and entries.
- `--force`: proceed for this store's links and state entry, but the
  referenced source **file is retained in place** and reported as
  `retained_sources[]` in the JSON envelope. Never destroyed while
  referenced — the referencing stores' entries are the next problem, not
  collateral damage.

`remove` on the *consumer* side is ordinary: unlink, drop the entry. The
source file is not the consumer's to touch.

## 5. Doctor, agent surface, schema

### Doctor

New findings:

- **warning** `alias-symlink`: a repo-internal symlink inside a store dir
  that resolves into the repo (the legacy workaround pattern). Message
  points at the `sources` migration. This is what flags my own dots repo
  until migrated.
- **error** (mirrors §1 validation): source escapes repo, source under
  `.stitch/`, source is a symlink, files/sources key collision.

### Agent JSON (docs/agent-schema.json)

- `plan`/`apply` ops carry `source` alongside `name` for file ops (additive,
  optional field — plain entries keep the implicit source).
- `add --json`: `source` field when registered via `--source`.
- `remove --json`: `retained_sources[]`.
- **Reverse lookup**: `stitch why <repo-relative-path>` on a source file
  answers "consumed by: `<store>:<target-path>` …" — the fan-in visibility
  query. `why <target-path>` gains `source` in its output. This is the one
  genuinely new query surface; it is what lets an agent answer "if I edit
  the hub, what changes" without grepping state.toml.
- `status` marks source-mapped links (`AGENTS.md ← agents/AGENTS.md`) so
  shared files are visible in the plain-text tree, not only in JSON.

## 6. Compatibility

State structs use `deny_unknown_fields`, so an **old binary on a new state
hard-refuses at load** — loud error, no silent drift, no partial apply.
That is the correct failure mode and the accepted rollback story: roll back
the binary and the state together (git both). A `state_version` key would
trip the same refusal, so it buys nothing; not added. `stitch.toml` is
untouched — `sources` is generated-inventory vocabulary, not behavior.

## 7. Tests (red-line coverage)

1. Hub fan-in integration test mirroring the dots layout: one real file,
   one multi-target store with a rename (`rules.md`), one external consumer
   store (`pi`), assert all links healthy and `diff` clean.
2. Sweep: store's own virtual link kept; link repointed away from a
   declared source → swept; link into another store's dir → untouched.
3. `remove` with inbound source refs: refuses; `--force` retains sources
   (filesystem assertion, not just JSON).
4. `add --source`: registers without touching the filesystem; add of an
   existing link-into-repo registers a source, no move.
5. Import re-derivation: links into another store's dir land as `sources`
   on the target-dir owner.
6. Load validation: each §1 error case (escape, `.stitch/`, symlinked
   source, files/sources collision, pattern collision, whole-dir store).
7. Old-binary-on-new-state: pinned refusal error (compat test).
8. Template via shared source: two stores render independently into their
   own staging.
9. Alias-symlink doctor warning fires on the legacy layout and clears after
   migration.

## 8. Implementation order

1. `types.rs` + `load.rs`: field, validation, merged view. (Everything else
   fails to compile until `LinkTargets` consumers are updated — do 2 with it.)
2. `resolve.rs`: `FileLink`, call-site sweep across apply/plan/report.
3. Sweep + scan/prune ownership predicates.
4. add `--source` + link adoption; remove refusals/retention.
5. Doctor findings; `why` reverse lookup; status marker; agent-schema.json.
6. Import re-derivation.
7. Tests 1–9, CHANGELOG, SPEC.md §state-shape update.
8. **Dots migration** (see §9), then release v0.14.0.

## 9. Dots migration (the consumer side, driver-executed)

After 0.14.0 installs:

1. `stitch add`/hand-edit state (hand-edits are legal) to:
   - `pi` store: `sources."AGENTS.md" = "agents/AGENTS.md"`, drop `AGENTS.md`
     from `files`.
   - `agentsconfig` store: same shape.
   - `agents` kilocode target: `sources."rules.md" = "agents/AGENTS.md"`.
2. `trash agents/rules.md agentsconfig/AGENTS.md pi/AGENTS.md` (the aliases).
3. `stitch doctor` (expect the alias warning to clear), `stitch diff
   --exit-code` → 0, `stitch apply` no-op.
4. Rewrite dots AGENTS.md "AGENTS.md fan-in" section: aliases → `sources`,
   remove the "safe from the stale-link sweep only because…" caveat.
5. Commit dots; tag stitch v0.14.0.

End state: `agents/AGENTS.md` is the only real file; seven links, zero
repo-internal symlinks, zero one-file workaround stores' magic.

## Out of scope for v0.14

- Multiple stores sharing one target directory (rejected, §1).
- Nested targets within a store (rejected, §1).
- Chained/multi-hop sources (forbidden, §1).
- `sources` on whole-dir stores (forbidden, §1).
- Copy-instead-of-link file delivery — still a symlink manager.
