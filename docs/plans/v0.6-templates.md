# v0.6 — Templates

Design sketch for the v0.6 templates milestone. Source: design pass on
2026-07-06; extends the contract already documented in `SPEC.md` §Templates.
Secrets are deliberately split out into v0.7 (separate trust surface) and are
mentioned here only where the template design must leave room for them.

Revised 2026-08-03 after an adversarial review pass: twelve challenges were
raised against the original sketch and resolved; §1, §4–§8 carry the
resolutions. All formerly open questions are now decided (§8).

State: **implemented** (slices A–F). See `src/render.rs` and the v0.6
checklist in `SPEC.md`.

---

## 0. Headline finding: staging must live inside the repo

An earlier draft of the SPEC put rendered files at
`~/.local/state/stitch/<repo-hash>/` — **outside the repo.** That silently
breaks three load-bearing pieces of code:

- `linker.rs::points_into_repo` returns `false` for any symlink that does not
  resolve under `repo_root`.
- `linker.rs::remove_link` guards every unlink on `points_into_repo` — so a
  templated symlink pointing at `~/.local/state/...` would be treated as
  **foreign** and removal would be refused.
- `scan.rs` (prune) only lists symlinks that point *into the repo* — templated
  links would be invisible to it entirely.

Net effect: every templated file would look like a chezmoi/stow-managed
conflict to stitch's own machinery.

**Fix (applied to `SPEC.md` 2026-07-06):** staging lives at
`.stitch/render/<store>/...`, inside the repo. It is already covered by
`GLOBAL_IGNORES` in `store.rs` (`.stitch` + `.stitch/**`), so resolution can
never recurse into it. The symlink still resolves into `repo_root`, and
`points_into_repo` / `remove_link` / `prune` work unchanged. This is the
single most important decision in the milestone.

## 1. Render → staging → symlink flow

```
repo store:   git/gitconfig.tmpl      ← you edit this
                          │ apply
                          ▼
              .stitch/render/git/gitconfig   ← generated; gitignore enforced (§5)
                          │ symlink
                          ▼
              ~/.gitconfig  ── points into repo ✓
```

Per store at `apply` time:

1. Scan for `*.tmpl` files **at any depth** — the suffix is the sole template
   signal (§8.2).
2. Render each **in memory** (never a tempfile — §5) and write atomically
   (`atomic_write`, mode `0600`) to
   `.stitch/render/<store>/<name-without-.tmpl>`. Render happens *before*
   link: a failed render skips the link entirely (§5 failure model).
3. Link the target to the rendered file (instead of the store source).
4. Non-`.tmpl` files take the existing direct-symlink path unchanged.

Whole-dir stores containing any `.tmpl` file are promoted to file-mode
resolution. Unlike ignore-promotion's top-level scan (`store.rs`), the
template scan **walks the full store tree** — templates nest
(`git/hooks/pre-commit.tmpl` must render, not link verbatim as a literal
`.tmpl`). Promotion replaces one directory symlink with N per-file symlinks:
invisible for `~/.config/git`, observable for watched dirs (`conf.d`,
systemd units, file watchers). This granularity change is a documented
behavioral consequence in SPEC, not a surprise.

Directory templates (a templated tree) are explicitly out of scope for v0.6;
templates are per-file.

## 2. Engine choice — the real decision

The roadmap historically said "Go-style `text/template`." There is no mature
Rust crate that reproduces Go's exact syntax. The honest options:

| Crate | Syntax | Sandbox | Fit |
|---|---|---|---|
| **minijinja** | Jinja2 (`{{ }}`, `{% %}`) | ✅ sandboxed by default, serde-native | recommended |
| upon | minimal `{{ }}` | partial | simple, less expressive |
| handlebars | `{{ }}` + helpers | logic-heavy | familiar, overkill |

**Decision (2026-07-06): minijinja.** Rationale, in priority order:

1. **Sandboxing matters once secrets arrive in v0.7.** A tool rendering
   templates that may interpolate secrets cannot let a template reach the
   filesystem. minijinja is sandboxed by design — no FS access, no arbitrary
   method calls, value access structurally bounded. This is the v0.7 secrets
   red line, designed in now.
2. **Error quality.** Template errors must name file + line (a red line).
   minijinja gives source-span errors; the Rust Go-clone (`gtmpl`) has
   documented line-number breakage fixed only in a heavy-dep fork.
3. **serde integration is free context.** The existing `[vars]` table and the
   `Platform` struct serialize straight into the render context.

Cost accepted: syntax is Jinja, not Go dot-notation. The SPEC table is updated
to match (`{{ hostname }}`, `{{ env("VAR") }}`). The tradeoff analysis
(minijinja vs gtmpl vs homegrown) lived in the 2026-07-06 design pass.

**Concrete wiring (implementation slice B):**

- `env.set_auto_escape(|_| minijinja::AutoEscape::None);` — dotfiles are
  plaintext; `&` must never become `&amp;`.
- `env.add_function("env", env_fn);` where
  `env_fn(name: &str, default: Option<String>) -> Result<String, Error>` — the
  one-arg form hard-fails on a missing var (red line: no silent empty
  substitution); the two-arg form supplies the default.
- Context built from `Platform` (serde) + the `vars` map; `secret` is added in
  v0.7 via the same `add_function` path — no rearchitecture.

Cost: syntax is not literally Go's. See open question 1.

## 3. Render context (one serde struct)

```rust
struct Ctx {
    os, arch, distro, hostname, shell,  // straight from platform.rs::Platform
    vars: Map<String, String>,           // [vars] in stitch.toml — already in SPEC
}

// Engine functions (minijinja `add_function`), not context fields:
//   {{ env("EDITOR") }}      → std::env::var, hard-fail if unset
//   {{ env("EDITOR", "vi") }} → two-arg form, opt-in default
//   {{ secret("token") }}    → v0.7, same context, no rearchitecture needed
```

`Platform` already detects every field the context needs (`platform.rs`).
`[vars]` is already an authored field in `stitch.toml`. No new config surface
for v0.6 — the milestone wires existing data into a render step.

## 4. `edit <entry>` — one verb, arg-disambiguated

History: the first draft of this section proposed an `edit` guard against
behavior that never existed (`stitch edit` opens `stitch.toml`, never a
symlinked target); the second proposed a separate `modify` command. Both were
conceded under review on 2026-08-03 — two verbs for "open a thing in
`$EDITOR`" was under-defended.

- `stitch edit` (no args) → `stitch.toml`, unchanged.
- `stitch edit <entry>` → the entry's **repo source**: the `.tmpl` for a
  templated entry, the plain file otherwise. **Never the staged render** —
  that is the drift footgun; staged output is regenerated on every `apply`.
- **Addressing is config-based, not symlink-walking.** The arg is resolved
  against the merged config: a store name opens its source; otherwise the arg
  is home-expanded and reverse-matched against configured targets → owning
  store + file. Works pre-apply (fresh machine) because it reads config, not
  filesystem links. The reverse lookup is a bounded subset (target path →
  store, then file) — not a reimplementation of glob/pattern/ignore
  resolution.
- Non-templated entries add little (the symlink target already *is* the repo
  source) but are allowed; the only invariant is "never open the staged
  file."

## 5. Honest failure modes (red lines)

- **Template parse error** → that entry fails: `ApplyAction::Error`, naming
  the file + line.
- **Missing `env`/`var` (one-arg form)** → same per-entry failure, naming the
  key. No silent empty-string substitution — that is exactly the "surprise
  the user" class the red lines forbid. Two-arg `{{ env("X", "default") }}`
  is the opt-out.
- **Failure model is per-entry, matching conflict aggregation.** Render
  happens *before* link via `atomic_write` — no partial staged file, and a
  failed render means the link is **skipped** (never created, never broken).
  `apply` continues with other entries and stores, then exits non-zero at the
  end if anything failed — the same way store A's conflict never rolls back
  store B. No transactional all-or-nothing; no half-written staging.
- **Staging is locked down from day one — not deferred to v0.7.**
  `.stitch/render/` is `0700`, renders are `0600`. v0.6 is not secret-free
  once `env()` can pull a token, and v0.7 must inherit a locked-down surface,
  not a 0644 default. All rendering (apply *and* diff) is **in-memory only**;
  no tempfile ever holds rendered plaintext under a default umask. SPEC
  documents the threat model: multi-user box, git group, shared CI runner.
- **Render output would land on a non-staged real file** → existing `Conflict`
  path, not a clobber. Foreign symlinks remain conflicts even under `--force`.
- **Rendered output must never enter version control.** `.stitch/render/`
  will hold plaintext secrets once v0.7 lands, and it sits inside the repo
  working tree — one `git add -A` from permanent history. `GLOBAL_IGNORES`
  only stops stitch from *linking* `.stitch`; it does nothing for git.
  Mechanism: `init` appends `.stitch/render/` to the repo's `.gitignore`;
  `doctor` errors if the entry is missing. Designed in now (v0.6) so v0.7
  adds no new exposure surface.
- **Name collisions are rejected.** A store containing both `foo` and
  `foo.tmpl` resolves both to the same link name. Reject at resolution time —
  the same class as the existing repo-content collision rule, extended to
  (real file, stripped-`.tmpl`) pairs.

These all extend existing behavior; nothing new is invented.

## 6. Idempotency & diff

- Render in memory, hash-compare against the staged file, skip the write if
  unchanged (preserves mtime, keeps `apply` cheap to re-run).
- Re-render on every `apply` (vars/env can change between machines); the
  hash gate makes this cheap.
- **`diff` gains a content dimension for templated entries only** — a named
  semantic extension in SPEC, since `diff` today is link-state-only
  (`cmd_diff` is `cmd_apply` dry-run). For a templated entry, `diff` renders
  fresh in memory and compares against the **staged** file. "Diff against the
  live target" would be tautological — the target is a symlink to staging, so
  staged ≡ live. The useful question is "would `apply` change anything?":
  non-empty after a source edit with no apply (staged is stale), empty after
  apply. Non-templated entries keep today's link-state behavior, unchanged.
- **Staging is reconciled, not just written.** `apply` removes staged renders
  whose source `.tmpl` no longer exists (deleted or renamed), and the target
  link's lifecycle follows the *template's* existence. Otherwise a removed
  template leaves a symlink pointing at a frozen artifact that silently never
  updates — the "surprise the user" class the red lines forbid. Same
  "config is truth" rule as link reconciliation, applied to `.stitch/render/`.
  **`remove` likewise deletes the entry's staged render** alongside its link.
- **Hand-edits to staging are surfaced, not preserved.** `.stitch/render/` is
  tool-owned and gitignored (like `state.toml`); a hand-edited render is
  overwritten on the next `apply`, and that is by design. But the clobber is
  never silent: `doctor` flags drift (staged ≠ fresh render) so the user
  knows staging is stale and will change. The supported edit path is the
  `.tmpl` source — with or without `edit <entry>`.

## 7. Proposed implementation order

| # | Slice | Touches | Depends on |
|---|---|---|---|
| A | **Trust foundation**: `.gitignore` enforcement (`init` writes, `doctor` verifies), `.stitch/render` permission contract (`0700`/`0600`), SPEC threat-model docs | `main.rs` (init/doctor), `SPEC.md` | none — **lands first**. v0.7's trust surface depends on it; it must not slip with the render work |
| B | **Core render**: `.tmpl` detection at any depth (promotion walks the full store), render→staging→symlink (in-memory, atomic, render-before-link, skip-on-error), collision rejection, source-name recording in state, SPEC granularity-consequence docs | new `render.rs`, `store.rs`, `linker.rs` callers | A |
| C | `env("VAR")` function + context fields (`vars`, `hostname`, `os`, …) + hard-fail semantics | `render.rs` | B |
| D | Idempotent hash-gated writes + staging reconciliation (incl. `remove` cleanup) + `diff` content dimension (templated entries only) + `doctor` drift flag | `render.rs`, `main.rs` | C |
| E | `edit <entry>` — config-based reverse resolution, opens repo source, never staged | `cli.rs`, `main.rs` | B |
| F | (separate) `import` — scan existing symlinks into state | `scan.rs`, `config.rs` | none — can land first if desired |

Slice A is small, independently reviewable, and deliberately decoupled from
the render feature so the trust foundation ships even if rendering slips.
Slice F (`import`) is independent of templates and builds only on existing
`scan.rs`. It can ship before or after the template slices without conflict.

## 8. Decisions (formerly open questions — all resolved)

1. ~~**Engine** — minijinja or literal Go `text/template`?~~ **Resolved
   2026-07-06: minijinja.** SPEC syntax updated to Jinja. See §2.
2. ~~**Naming** — `.tmpl` suffix vs chezmoi-style `dot_` prefix?~~
   **Resolved 2026-08-03: `.tmpl` suffix.** Decision rule: detection must be
   deterministic from the directory entry alone, no content read — apply
   walks many files (content-scanning is waste), and a false-positive render
   breaks a user's config *silently and unsolvably*, whereas lost editor
   filetype highlighting is user-fixable (ftplugin/modeline; ship a docs
   snippet). That rules out content sentinels and front-matter. `.tmpl` over
   `.j2` because the engine is an implementation detail, not a user-facing
   contract. Cost owned: users who want syntax highlighting add an editor
   rule — a docs problem, not a mechanism.
3. ~~**Missing env/vars** — hard-fail or empty-default?~~ **Resolved:
   hard-fail.** §5 lists it as a red line; the two-arg
   `{{ env("X", "default") }}` form is the opt-out.
4. ~~**`modify` scope/addressing**~~ **Resolved 2026-08-03: folded into
   `edit <entry>`** — one verb, arg-disambiguated, config-based addressing
   (§4). The separate command was under-defended.
5. ~~**File-mode mapping** — list `gitconfig` or `gitconfig.tmpl`?~~
   **Resolved 2026-08-03: source names.** `files`/`patterns` name the
   template source (`gitconfig.tmpl`); patterns match names as they exist in
   the store (pre-strip). `state.toml` likewise records source names, and
   apply/status/remove/diff all strip via the same `resolve_entry` — the
   source name exists on disk, so `list` is honest. Invariant: *never use a
   store file name directly as a link target.* Recording the stripped link
   name would force apply to re-derive `.tmpl` (lossy when both exist).

## Out of scope for v0.6

- Encrypted secrets (`{{ secret }}`, `.stitch/secrets.enc`, key management) →
  v0.7. Designed to slot into the same render context; no rearchitecture.
  The `.gitignore` enforcement in §5 ships in v0.6 precisely so v0.7 adds no
  new exposure surface.
- Directory templates (templated trees, not just files).
- `add --template` / a `template` subcommand (adopt-and-templatize) →
  post-v0.6 nicety. v0.6 authoring is **hand-written**: drop
  `gitconfig.tmpl` into a whole-dir store (promotion picks it up, no state
  edit), or rename + list it in `files` for file-mode stores. Documented
  plainly so users don't hunt for the chezmoi-style command.
- TUI render preview → v0.8.
