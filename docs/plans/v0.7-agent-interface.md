# v0.7 — Agent interface

Design for the v0.7 milestone: `--json` on read/plan commands, a
`plan` → `apply --plan` primitive (verbatim execution, no re-derivation),
and distinct exit codes per failure class with resolution hints.

Source: agent-feedback pass on the stow→stitch migration (2026-08-03). The
session verified state by hand (`readlink -f`, `grep -c`, eyeballing prose)
and hit a TOCTOU window between `import --dry-run`, `stow -D`, and `apply`.
Three requirements fell out: verification as structured data, an
approve-then-execute-exactly-this primitive, and branchable failures an
agent can self-recover from.

State: **planned** — four decision points ruled 2026-08-04:

1. **Roadmap renumber approved.** v0.7 takes the slot previously assigned to
   encrypted secrets (→ v0.8); TUI → v0.9. Secrets remain a separate trust
   surface and are not mentioned further here.
2. **`stitch render` is in scope.** The feedback referenced a
   `render-preview` command that does not exist (v0.6's surface is `init,
   apply, status, diff, list, add, remove, edit, import, doctor, migrate,
   prune` — `src/cli.rs`). It is added here as `stitch render`.
3. **Plan execution aborts at the first failed op** (deliberate divergence
   from `apply`'s continue-and-aggregate). Ruled in §2.
4. **Exit-code table approved** as written in §3.
5. **`doctor`-with-errors gets its own class (exit 13)** — ruled 2026-08-04
   on the M1 gap review. Doctor findings are the command's purpose, not io or
   unexpected, so `Internal` (exit 1) was a semantic stretch. Added as
   `FailureClass::Doctor` / code 13; the §3 table gains a row.

## 0. Headline decision: one compute path

All three features sit on a single refactor — **split compute from present,
and compute from execute.** Today `store::apply_all` classifies, executes,
and previews in one pass (a `dry_run` bool threaded through everything),
`diff` is literally `cmd_apply` with `dry_run: true`, `main.rs` prints prose
inline while matching on `ApplyAction`, and every error is a
`format!(...).into()` string → exit 1.

The v0.7 core is one function:

```
compute_plan(root, config, platform, opts) -> Plan
```

- `apply` = compute_plan + execute immediately
- `diff` = compute_plan + text render
- `stitch plan` = compute_plan + JSON envelope to stdout
- `stitch apply --plan <file>` = deserialize + validate + execute
- `--json` on any command = serialize the same structs the text renderer
  consumes — so text and JSON **cannot drift apart**

"No re-derivation" is then structural, not a parallel codepath to keep in
sync. `ApplyAction` (Created/Replaced/BackedUp/Conflict/Removed/Error/…)
already exists and is ~90% of the op vocabulary, but it records targets
only; the `Plan` type upgrades each action into an executable op carrying
the source paths and preconditions needed to replay it.

## 1. `--json` everywhere

Global `--json` flag (sits next to `--repo`). Applies to: `status`, `list`,
`diff`, `doctor`, `apply [--dry-run]`, `plan`, `add --dry-run`,
`remove --dry-run`, `import [--dry-run]`, `prune`, `migrate --dry-run`,
`render` (new).

### Envelope

Stable, versioned, boring:

```json
{
  "schema": 1,
  "command": "status",
  "ok": true,
  "warnings": [],
  "data": { "...": "command-specific" },
  "error": null
}
```

- **One-stream rule:** under `--json`, the envelope — *including* the
  `error` object on failure — goes to **stdout**; the exit code stays
  honest. Agent pattern: `out=$(stitch apply --json)`; branch on `$?`, parse
  `$out`. stderr is reserved for hook passthrough.
- Load warnings (`print_warnings`, stderr today) become `warnings[]`
  entries.
- On failure, `error` is `{class, code, message, hint, details}` (§3).

### Per-command shapes

Chosen so the session's assertions are one `jq` each:

- `status --json`:
  `[{store, target_name, target, source, templated, staged_path, state:
  linked|missing|conflict|broken, resolves_to}]` — "zero broken links",
  "machineid resolves via store X", "2 are templated".
- `list --json`: stores, targets, multi-target names, `when` clauses,
  file-mode vs whole-dir.
- `doctor --json`: findings become **typed** — `DoctorResult` is three
  `Vec<String>` today. Each finding gains
  `{id, severity, message, path?, hint?}` with stable IDs (`broken-link`,
  `missing-store-dir`, `orphaned-behavior`, `staging-drift`, …) so consumers
  filter by ID instead of grepping prose. Text output keeps its current
  shape.
- `diff --json` / `plan`: the op list (§2 format).

### Schema stability

Additive-only changes within a minor version. Schemas are documented in
`SPEC.md` and locked by golden tests — `tests/cli.rs` parses output with
`serde_json` and asserts shape + values.

### New dependencies

- `serde_json` (deps + dev-deps) — envelopes and golden tests.
- `sha2` — plan/config/render hashes. Nothing in-tree hashes today; the
  v0.6 hash-gating is a string compare.

### New command: `stitch render <store>/<file>`

Prints the fresh in-memory render of one `.tmpl` to stdout. `--json` gives
`{source, link_name, sha256, content}`. Read-only — no staging write, no
link touch. Rendered content may contain `env()`-pulled values; printing to
your own terminal is the user's explicit act (same as `pass show`).

## 2. `stitch plan` → `stitch apply --plan <file>`

The TOCTOU killer: capture an exact operation list, inspect it as JSON,
execute that list verbatim. If the world shifted between capture and exec,
exec fails loudly instead of silently applying something unapproved.

### Plan format

```json
{
  "schema": 1,
  "kind": "stitch/plan",
  "repo": "/home/daniel/dots",
  "config_sha256": "…",
  "platform": {"os":"linux","arch":"x86_64","distro":"arch","hostname":"x","shell":"zsh"},
  "ops": [
    {"op":"stage_render","store":"git","source_rel":"gitconfig.tmpl",
     "staged":"…","sha256":"…"},
    {"op":"create_link","target":"…","source":"…",
     "requires":{"target":"absent"}},
    {"op":"replace_link","target":"…","source":"…",
     "requires":{"target":"symlink_to","value":"…"}},
    {"op":"backup_and_link","target":"…","backup":"….bak","source":"…",
     "requires":{"target":"real_entry","backup":"absent"}},
    {"op":"remove_link","target":"…",
     "requires":{"target":"symlink_into_repo"}}
  ],
  "conflicts": [
    {"target":"…","kind":"foreign_symlink","resolves_to":"…"}
  ]
}
```

### Mechanisms

- **Renders are pinned by hash, never embedded.** `stage_render` carries the
  `sha256` of the approved render; exec re-renders and verifies *identity*.
  An env var that shifted since capture → stale-plan failure, not a silent
  divergence. Side benefit: the plan file holds **no plaintext**, so
  `stitch plan > /tmp/p.json` is safe anywhere — v0.6's `0600`/`0700`
  staging discipline is not undermined by a secret-laden plan file.
- **Config + platform fingerprints pin everything config-derived** —
  including hooks. Hooks are therefore not plan ops: exec runs them from the
  pinned config, and `config_sha256` guarantees they are what was approved.
  Any edit to `stitch.toml`/`state.toml` between capture and exec → hard
  refusal (exit 12), re-plan. Same for hostname/OS drift — plans are
  single-machine artifacts.
- **`requires` preconditions close the window twice.** Preflight *all*
  preconditions before executing anything (fail-before-mutate, matching
  `migrate`'s invariant), then re-check each op's precondition immediately
  before executing it (the `remove_link_to` check-then-act pattern).
- **Abort at the first failed op** (ruled). Ops are ordered — renders before
  their links, per store — and the approved artifact is the whole list. A
  prefix-executed, clearly-reported state is more honest than a best-effort
  splatter. The abort report states exactly which ops executed and which
  remain. This diverges from `apply`'s continue-and-aggregate on purpose:
  apply is a reconcile, plan-exec is a transaction-ish replay.
- **Removals route through the existing guards** — `remove_link` /
  `remove_link_to` re-check `points_into_repo` at unlink time. Foreign
  symlinks are never ops; they appear in `conflicts[]` as data, exactly as
  today. A link repointed between capture and exec fails its precondition
  (or, in the gap, the guard) and is never clobbered.
- **The plan file is untrusted input.** A hand-edited plan could point ops
  anywhere, so load-time validation re-checks every op against the *pinned*
  config: targets must fall under a declared store target or
  `.stitch/render/`; sources must live under the repo; fragments pass
  `validate_fragments`. An op no store justifies → reject the plan. This is
  a security boundary, not a nicety.

### Scope boundary

Plans cover `apply` reconciliation only: links, staged renders,
stale-link/staging cleanup, `--force` backups. `add` / `remove` / `import`
keep `--dry-run` + `--json` previews but get **no** executable plans — they
write `state.toml`, a different mutation class.

### CLI shape

- `stitch plan [--only …] [--force]` → plan JSON on stdout (mirrors `diff`'s
  flags).
- `stitch apply --plan <file>` executes it. Combining `--plan` with
  `--only`/`--force` is a usage error (exit 2) — verbatim means verbatim.
- `stitch apply --plan <file> --dry-run` = preflight-only: validate every
  precondition and fingerprint, mutate nothing. A genuinely useful
  composition.

### Exit semantics

- `plan` mirrors `diff`: exits non-zero (class code) when the captured plan
  contains conflicts, so `stitch plan && stitch apply --plan p.json` forces
  a branch. The plan JSON is still emitted.
- Exec runs the ops (conflicted entries were never ops), reports conflicts
  in the envelope, exits with the conflict class.

## 3. Exit codes + hints

New `src/error.rs`: a `StitchError` enum (thiserror) with class →
`exit_code()` + `hint()`. `main` maps typed errors instead of today's
blanket `exit(1)`. Under `--json` the envelope's `error` carries
`{class, code, message, hint, details}`; text mode gains a `hint: …` line on
stderr.

| Code | Class | Hint example |
|---|---|---|
| 0 | ok | |
| 1 | generic/internal (io, unexpected) | |
| 2 | usage (clap native; also `--plan`+`--force`) | |
| 3 | config load/parse, v0.2 repo detected | `run stitch migrate` |
| 4 | repo resolution (no `.stitch/`, bad `--repo`) | |
| 5 | unknown store name | lists valid names |
| 6 | conflict: real file/dir at target | `stitch add <path>` or `apply --force` |
| 7 | conflict: foreign symlink | remove it yourself; stitch never clobbers |
| 8 | render failure (missing env var, template parse) | `set STITCH_MACHINEID` / fix template |
| 9 | path validation (absolute/`..` fragment, `foo`+`foo.tmpl` collision) | |
| 10 | hook failure | |
| 11 | mixed/partial (multiple failure classes in one run) | per-entry classes in JSON |
| 12 | plan not executable (stale precondition, config/platform drift, bad plan schema) | re-run `stitch plan` |
| 13 | doctor reported error-severity findings | address the findings (per-finding hints in JSON) |

**Aggregation rule** for `apply` (which continues per-entry): a single
failure class present → that class's code; multiple classes → 11, with
per-entry classes in the JSON envelope. Deterministic and documented.

`diff` / `plan` keep today's "conflicts → non-zero" behavior, upgraded from
1 to the class code.

## 5. Red-line interaction

Every existing trust invariant is preserved; two are strengthened:

- **Foreign symlinks are conflicts, not replacements** — never plan ops;
  removals keep routing through the `points_into_repo` guards, re-checked at
  unlink time.
- **No destructive overwrite** — `backup_and_link` exists only in plans
  captured with `--force`; its `backup: absent` precondition means a `.bak`
  collision fails at preflight *and* at exec, before anything moves.
- **Honest exit codes** — extended into a documented, branchable table;
  `diff`/`plan`/`apply --plan` semantics stated above.
- **Path validation** — plan files are validated as untrusted input against
  the pinned config (new boundary; see §2).
- **Authored config is read-only** — plan exec writes staged renders and
  links only; `state.toml` and `stitch.toml` are untouched (plan scope is
  `apply`, which never writes either).
- **No external upload** — unchanged; plans are local files, hashes only, no
  network surface added.
- **No data exposure** — plan files contain paths and hashes, never rendered
  content; `stitch render` prints to the user's own terminal only on
  explicit request.
