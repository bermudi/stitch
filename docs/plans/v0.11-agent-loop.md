# v0.11 — Agent loop

Design for closing the gaps an LLM-driven loop hits when driving stitch
end-to-end. v0.7 shipped the foundation (`--json` envelope, typed exit codes,
`plan` → `apply --plan`, `doctor` findings). v0.8 hardened the trust surface.
This milestone makes the **mutating** commands first-class JSON citizens and
turns the error taxonomy from "branchable by class" into "branchable by
action," so an agent can converge and self-recover without a second
round-trip or prose parsing.

Source: review of the agent surface on 2026-08-14. The primitives are right;
the gaps are (a) mutations are JSON-blind, (b) recovery hints are prose, (c)
there is no single resolved-desired-state view, (d) shapes are documented in
prose only. Version number is provisional — v0.9 (secrets) and v0.10 (TUI) are
already planned; this slots after both. It is independent of either and could
ship earlier if renumbered.

State: **proposed** — awaiting approval before implementation.

---

## 0. Headline: one-shot transactional calls

The throughline across every item below: an agent wants **one call that
returns the full relevant state**, not a toolkit it orchestrates. Today the
main loop is `diff` → `apply` → `status` (three calls, with the agent
mentally merging the results). The flagship change in §3 makes `apply --json`
return `{desired, plan, result, post_status}` so the converge-and-report loop
is one call. Everything else either feeds that envelope or removes a
round-trip from a recovery path.

Red lines from `AGENTS.md` are unchanged and upheld: no external upload,
foreign symlinks stay conflicts, honest exit codes, path-fragment validation,
no destructive overwrite, race boundary as documented, no hidden quarantine,
authored config read-only to the tool, `prune` list-only by default. None of
this work weakens them; §2 (recovery hints) and §1 (mutation JSON) are
strictly additive reporting.

## 1. JSON on real mutations (highest leverage)

### Problem

`add`/`remove`/`migrate`/`init` only emit JSON under `--dry-run` (see
`src/commands/add.rs:1149` — `--json` without `--dry-run` exits 2). An agent
runs the real mutation blind, then re-queries `status`/`list` to learn what
happened: two round-trips and a silent verification gap.

### Change

Lift the `--dry-run`-only restriction for `add`, `remove`, and `migrate`.
After a successful real mutation, emit the same envelope with a post-op
report. `init` stays non-JSON (it creates two files and a gitignore line;
there is nothing to report that `list` wouldn't show — keep it text-only and
documented as such).

Post-op report shapes (additive to existing `AddData`/`RemoveData`/`MigrateData`
in `src/report.rs`):

- `add --json` (real): `{store, target, mode, source?, files[], patterns[], moved_from?, link_created, state_entry}`.
  `moved_from` is the original path when an adopt moved content into the repo
  (so the agent can verify the move and report it to the user). `link_created`
  is the absolute symlink path. `state_entry` is the new `state.toml` slice
  for this store.
- `remove --json` (real): extend current `RemoveData` with `removed_links[]`,
  `removed_staging[]`, `state_entry_removed: bool`, `behavior_orphaned: bool`
  (the `stitch.toml` behavior left in place — flags the `doctor` warning the
  agent should expect).
- `migrate --json` (real): `{authored_path, state_path, backup_path,
  stores_split: usize, comment_loss_note: true}`.

### Exit codes

Unchanged. A successful mutation is exit 0 with `ok: true`. Partial failure
isn't possible for these single-store commands (they're atomic — either the
move+link+state-write happens or it doesn't), so no `mixed`-class concern
here. Conflicts and validation failures keep their existing classes (6, 7, 9,
…).

### Touchpoints

- `src/cli.rs`: no change (the `--json` flag already exists globally; the
  gate is in command code, not clap).
- `src/commands/add.rs`: remove the `json && !dry_run` → exit 2 branch at
  `:1149`; thread a post-op `AddData` build after the successful
  move/link/state-write. The dry-run preview shape stays as-is.
- `src/commands/remove.rs`, `src/commands/migrate.rs`: same pattern.
- `src/report.rs`: extend `AddData`/`RemoveData`/`MigrateData` with the new
  optional fields (all `skip_serializing_if` so dry-run output is unchanged).
- `SPEC.md` §Agent interface: move `add`/`remove`/`migrate` out of the
  "dry-run only" list; document the post-op shapes.
- `tests/cli.rs`: golden tests for the post-op JSON on a real `add` and
  `remove` in a temp repo.

### Risk

Low. Pure reporting on the success path. The mutation logic is untouched; we
just build a struct from values already in scope after the operation
completes. The one thing to get right: the post-op report must reflect what
*actually* happened (read back the created symlink, confirm the `state.toml`
entry), not what we intended — that's the whole point for an agent verifying
convergence.

## 2. Structured recovery hints (`recoverable_via`)

### Problem

`ErrorDetail.hint` is free text (`src/report.rs:35`, `src/error.rs:344`). An
agent hitting `conflict-real` has to parse "remove or move `…`, or run
`stitch apply --force`" to decide what to do. That's an LLM-interpretation
step on the critical recovery path — exactly where autonomous loops break.

### Change

Add a machine-readable `recoverable_via` field to `ErrorDetail`. It is a list
of recovery actions, each a concrete command the agent can run verbatim or
branch on by `kind`:

```json
"error": {
  "class": "conflict-real",
  "code": 6,
  "message": "conflict: real file/dir at /home/daniel/.gitconfig",
  "hint": "remove or move `/home/daniel/.gitconfig`, or run `stitch apply --force`",
  "details": null,
  "recoverable_via": [
    {"kind": "force-apply", "command": "apply", "flags": ["--force"]},
    {"kind": "adopt", "command": "add", "args": ["/home/daniel/.gitconfig"]}
  ]
}
```

`details` stays as-is (the reserved slot for plan-stale precondition diffs).
`recoverable_via` is a new sibling field, always present, `[]` when the error
isn't recoverable (e.g. `internal`, `usage`, `path-validation`).

### Mapping (per error variant)

| Error | `recoverable_via` |
|---|---|
| `ConflictReal` | `force-apply` (`apply --force`), `adopt` (`add <target>`) |
| `ConflictForeign` | `manual` (no command — foreign symlinks are never auto-clobbered; `kind: "manual"` with a `reason` string) |
| `Render` | `edit-template` (`edit <source>`), `set-env` (`kind: "set-env"`, `vars: [...]` listing the missing `env()` keys when extractable) |
| `UnknownStore` | `list` (`list`) |
| `RepoResolution` | `init` (`init`) |
| `Config` (legacy v0.2) | `migrate` (`migrate`) |
| `PlanStale` | `replan` (`plan`) |
| `Drift` | `apply` (`apply`) |
| `Hook` | `manual` (with the hook `name` in `details`) |
| `Internal` / `Usage` / `PathValidation` / `Doctor` / `Mixed` | `[]` |

`manual` entries carry a `reason` field rather than a `command` — they tell
the agent "this needs a human or a non-stitch action," so it stops retrying
stitch commands and escalates instead of looping.

### Touchpoints

- `src/report.rs`: add `recoverable_via: Vec<RecoveryAction>` to `ErrorDetail`;
  thread it through `write_error` and `write_data_error`. `RecoveryAction` is
  a small serde struct.
- `src/error.rs`: add `fn recoverable_via(&self) -> Vec<RecoveryAction>` on
  `StitchError`, mirroring the existing `hint()` per-variant match. Extract
  missing `env()` keys for `Render` where feasible (parse the template once,
  collect `env("X")` calls without arguments); if extraction is unreliable,
  emit `set-env` with `vars: []` and let `hint` carry the detail.
- `SPEC.md` §Exit codes / §JSON envelope: document `recoverable_via` and the
  `kind` taxonomy. Note `manual` means "do not retry stitch commands."
- `tests/cli.rs`: golden tests that a `conflict-real` error envelope contains
  the two expected `recoverable_via` entries.

### Risk

Low-medium. The mapping is per-variant and exhaustive (the `StitchError` enum
is closed). The main design care: `recoverable_via` must never recommend an
action that violates a red line — e.g. it must **not** offer to clobber a
foreign symlink. The table above is conservative: foreign symlinks and hooks
are `manual`. If a future error variant is added without a mapping, the
`Default`/`[]` fallback keeps it safe (agent gets no recommendation rather
than a wrong one).

### Schema stability

This adds a field to `ErrorDetail`. `schema` stays `1` — additive fields on
existing objects are backward-compatible (an old parser ignoring unknown
fields still works). Document this in the schema-stability section.

## 3. Flagship: `apply --json` returns the full loop

### Problem

`apply --json` returns only the `Plan` (ops + summary). An agent then runs
`status --json` to verify convergence and `list --json` to know the desired
state. Three documents for one logical action.

### Change

Extend `apply --json`'s `data` to a composite envelope:

```json
{
  "desired": { ... resolved desired state, see §4 ... },
  "plan":    { ... existing Plan shape, unchanged ... },
  "result":  { ... per-op execution outcome, see below ... },
  "post_status": [ ... StatusRow[] for the applied stores ... ]
}
```

- `desired`: the host-evaluated merge (same struct as the new `explain`
  command in §4), so the agent knows what the world should look like without a
  separate call.
- `plan`: the existing `Plan` shape — unchanged, golden tests still pass.
- `result`: per-op outcome after execution. Today `apply` aggregates into
  `summary` counts; `result` adds per-op `ok`/`failed` with the error class
  for each failed op (so an agent sees *which* target failed, not just a
  count). On `--dry-run`, `result` is `null` and `post_status` reflects
  pre-apply state.
- `post_status`: `StatusRow[]` (reuse `src/report.rs:StatusRow`) for the
  stores in `--only` (or all if no `--only`), computed *after* execution.
  This is the verification the agent would otherwise do via a second
  `status` call.

`diff --json` and `plan --json` are **unchanged** — they stay lean (desired
state isn't executed, so the composite isn't needed). Only `apply --json`
gets the composite, because only `apply` both computes and mutates.

### Exit codes

Unchanged. Conflicts/errors still exit with their class code; the envelope
carries `ok: false` plus the composite `data` (partial success is already
represented by `plan` containing `conflict`/`error` ops).

### Touchpoints

- `src/commands/apply.rs`: after execution, build `post_status` by re-running
  the status computation for the applied stores; assemble the composite.
- `src/report.rs`: new `ApplyData { desired, plan, result, post_status }`.
  The existing `Plan` serializer is reused as `plan`.
- `src/store/status.rs`: already produces `StatusEntry[]`; reuse for
  `post_status`.
- `SPEC.md`: document the composite `apply --json` shape; note `diff`/`plan`
  are unchanged.
- `tests/cli.rs`: update the `apply --json` golden test to the composite
  shape; add a test that `post_status` reflects post-execution link state
  (create a temp repo, apply, assert `post_status[i].state == "linked"`).

### Risk

Medium. This changes an existing JSON shape, so it's the one item with real
backward-compat impact. Mitigations:

1. The `plan` sub-object is byte-identical to today's `apply --json` output —
   existing consumers that only read `data.plan` (or `data.summary`) keep
   working if they access by key.
2. Bump a note in the schema-stability section: composite `apply --json` is
   the v0.11 shape; consumers should read `data.plan` rather than treating
   `data` as the plan.
3. If a consumer treating `data` as the `Plan` directly is a concern, gate
   the composite behind keeping `data` as the plan and adding a sibling
   `applied` object instead — **open decision Q1 below**.

### Open decision Q1

Two shapes for the composite:

- **(A) Replace:** `data = {desired, plan, result, post_status}`. Cleaner,
  one shape going forward. Breaks any consumer that does
  `data.summary.created`.
- **(B) Additive:** `data` stays the `Plan`; add `applied: {desired, result,
  post_status}` as a sibling. Zero breakage, but two shapes coexist and the
  `Plan`-as-`data` convention gets awkward.

Recommend **(A)** with a schema-stability note, since the agent consumers this
targets don't exist yet in the wild and (B) permanently carries the
awkwardness. Confirm before implementing.

## 4. `stitch explain` — one resolved desired-state view

### Problem

No single JSON view of ground truth. An agent merges `list --json`
(configured), `status --json` (filesystem), and `diff --json` (delta) to
answer "what should the world look like here." `when` evaluation is the part
it can't do itself reliably.

### Change

New read-only command `stitch explain [--json]`. Emits the fully-resolved,
host-evaluated merge of `stitch.toml` + `state.toml`:

```json
{
  "platform": { "os": "linux", "arch": "x86_64", "distro": "arch", "hostname": "x", "shell": "zsh" },
  "stores": [
    {
      "name": "git",
      "active": true,
      "when": { "os": "linux" },
      "mode": "file-mode",
      "target": "/home/daniel/.config/git",
      "entries": [
        { "source": "gitconfig.tmpl", "templated": true, "link_name": "gitconfig" }
      ],
      "hooks": { "post": "git config --global core.editor nvim" },
      "ignore": ["*.bak"]
    }
  ]
}
```

- `active`: whether `when` matches this host (the `when`-evaluated-against-
  this-host bit the agent can't do).
- `entries`: per-file resolution (source name, `templated` flag, link name
  with `.tmpl` stripped) — the resolved inventory, not raw `files`/`patterns`.
- This is the `desired` object embedded in `apply --json` (§3), exposed
  standalone.

Text mode prints a human-readable summary (active stores, their targets,
entry counts). `--json` emits the envelope.

### Touchpoints

- `src/cli.rs`: new `Explain` variant (no args).
- `src/commands/explain.rs`: new; loads config, evaluates `when` via
  `src/platform.rs`, resolves entries via `src/store/resolve.rs`, builds the
  DTO.
- `src/report.rs`: `ExplainData` (reused as `desired` in §3).
- `SPEC.md`: new command section.
- `tests/cli.rs`: golden test for `explain --json` on a multi-store repo with
  a platform-skipped store (assert `active: false`).

### Risk

Low. Read-only, no mutation. Reuses existing config load + `when` evaluation
+ entry resolution — no new logic, just a new presentation of values already
computed internally.

## 5. `stitch schema` — self-describing shapes

### Problem

The envelope has `schema: 1` but an agent can't learn the shapes from the
tool — it reads SPEC.md and hopes it remembers field names. Hallucinated
field names are the dominant failure mode for LLM-driven JSON consumers.

### Change

`stitch schema --json` emits a JSON document describing:

- the envelope (`schema`, `command`, `ok`, `warnings`, `data`, `error`),
- every per-command `data` shape (status, list, diff, apply, plan, doctor,
  prune, render, add, remove, migrate, explain),
- the `error` shape including `recoverable_via` kinds,
- the exit-code table (`class`, `code`, `hint`),
- the plan-op shapes and `requires`/`TargetState` forms.

Output is a static JSON object (built from `serde_json::json!` literals or a
checked-in `docs/agent-schema.json` that the command reads and echoes). The
checked-in file is preferred — it's reviewable and the command is a one-line
read, so it can't drift from the spec by construction.

### Touchpoints

- `src/cli.rs`: new `Schema` variant.
- `src/commands/schema.rs`: new; reads `docs/agent-schema.json` and emits it
  in the envelope (or directly — `schema` is meta, so it may emit the document
  *as* the envelope's `data`).
- `docs/agent-schema.json`: new, the canonical schema document.
- `tests/cli.rs`: test that `schema --json` output parses and contains the
  expected top-level keys; test that every command's `data` shape documented
  in SPEC.md has a matching entry in the schema file (a consistency check).
- `SPEC.md`: reference `docs/agent-schema.json` as the canonical shape source.

### Risk

Low. Pure documentation-as-code. The only maintenance burden is keeping
`docs/agent-schema.json` in sync with shape changes — mitigated by the
consistency test above (it should fail the build if a `data` shape in code
diverges from the schema file, by serializing a sample and diffing keys).

## 6. Smaller, still-worth-it items

These are individually small and can be picked off independently or deferred.
Listed in priority order.

### 6a. `stitch why <target>` — single-path investigation

One command answering "what owns this path, what's its source, what's its
link state." Merges config + filesystem for one target. Replaces the agent
cross-referencing `list` + `status` + `doctor` when investigating a broken
dotfile. Output: `{store, target_name?, target, source, templated, state,
resolves_to?, owning_config: "state.toml"}`. Read-only.

### 6b. `stitch source <entry>` (or `edit --print-path`)

Non-interactive path resolution. `edit` opens `$EDITOR` (useless to an
agent); give the agent the repo path to open with its own tools. `status
--json` partially covers this for already-linked entries, but not pre-apply.
A `--print-path` flag on `edit` (or a new `source` command) returns the repo
path of an entry's source without launching an editor.

### 6c. `explain --active-only`

Stores whose `when` matches this host. Clean primitive for "what would apply
here" without scanning `status` for `skipped_platform`. Folded into `explain`
as a flag (Q2 decision) rather than a separate command — one shape, no struct
duplication.

### 6d. Audit log — `.stitch/log.jsonl`

Append one JSON line per mutating op (command, timestamp, store, target,
outcome, exit class). Readable via `stitch log --json` (paginated/limited).
Lets an agent verify post-hoc what actually happened without re-running
`diff`. Must respect the "no hidden state" red line: the log is visible,
documented, and `stitch log` is the only reader; it is not a quarantine or
retention mechanism. Default rotation/size cap to be decided — **open
decision Q3**.

### 6e. Bulk `add`

`add a b c` or `add --from manifest`. Fresh-machine setup is N round-trips
today; one transaction with one result envelope (an array of §1's post-op
`AddData`) is friendlier and easier to reason about atomically. Atomicity
rule: if any one add fails, prior adds in the batch are rolled back (or the
batch is all-dry-run-validated first, then applied — preferred, matches the
`plan`→`apply` philosophy).

### 6f. Hook correlation in error `details`

When a hook fails (exit 10), put `store` and which hook (`pre`/`post`,
global vs per-store) in `error.details`. Today the agent gets "a hook failed"
and reads stderr to find which one. Small change to `src/error.rs::Hook` and
the `details` field population in `src/report.rs`.

## Sequencing

Dependency graph (arrows = "enables or shares a struct with"):

```
§4 explain  ──┐
              ├──► §3 apply --json composite
§1 mutation json (independent)
§2 recoverable_via (independent)
§5 schema (independent, but should land after §1-§4 so it documents the final shapes)
§6a-§6f (independent, pick off anytime)
```

Recommended order:

1. **§2 recoverable_via** — smallest, highest impact on autonomous recovery,
   no shape breakage. Lands the `ErrorDetail` extension that §3/§5 build on.
2. **§1 mutation JSON** — closes the mutate-then-verify loop for the
   single-store commands. Independent, low risk.
3. **§4 explain** — read-only, lands the `desired` struct that §3 embeds.
4. **§3 apply --json composite** — the flagship; depends on §4's struct and
   §2's error shape. Resolve Q1 first.
5. **§5 schema** — documents the now-final shapes; consistency test backstops
   future drift.
6. **§6 items** — opportunistic.

Each step ships independently and is verifiable on its own. None requires the
others to land first except §3 ← §4 (struct reuse) and §5 ← (§1-§4 for
complete documentation).

## Open decisions — resolved 2026-08-15

The target consumer is an LLM agent driving stitch (not a human end user), so
decisions are optimized for agent use: fewer round-trips, machine-readable
recovery, one shape per concept.

- **Q1 → (A) replace.** `apply --json`'s `data` becomes the composite
  `{desired, plan, result, post_status}`. The agent consumer doesn't exist in
  the wild, so breakage isn't a concern; (B) would permanently carry two
  coexisting shapes. `data.plan` remains byte-identical to today's `data`, so
  key-access consumers keep working.
- **Q2 → `explain --active-only`.** One command, one shape; a separate
  `active` command would duplicate the `ExplainData` struct. The flag filters
  to stores whose `when` matches this host.
- **Q3 → unbounded + `--limit`.** Rotation is premature for a personal
  dotfile tool. `stitch log --json --limit N` reads the tail; the file grows
  unbounded and the user can truncate it manually. Rotation deferred to a
  future release if it ever matters.
- **Q4 → v0.11 as working label.** Renumber on ship if it lands before
  secrets (v0.9) or TUI (v0.10). Independent of both; could ship earlier.
