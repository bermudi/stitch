# v0.3 — Config/state split

Source: design session 2026-06-17 (session `…`). Contract captured in
`SPEC.md` §Config and the AGENTS.md "Authored config is read-only to the tool"
red line.

**Status: shipped 2026-06-18 (items 1–6 + 9; 7 partial — orphaned-behavior only; 8 deferred). Breaking.** v0.2 repos must run `stitch migrate` once.

## Why

v0.2 keeps authored config (user preferences: `when`, `hooks`, `ignore`,
`vars`) and generated desired state (link inventory: `target`, `files`,
`patterns`) in one file: `.stitch/config.toml`. Every mutating command
(`add`/`adopt`/`remove`) reserializes the whole file via
`toml::to_string_pretty` (`config.rs:98`), which drops comments and
hand-formatting because they aren't part of the data model. So adding an
unrelated store silently destroys the documentation on a user's behavioral
config. That is the motivating bug; it is not fixable inside the single-file
model.

The fix is a hard authorship boundary: authored content lives in `stitch.toml`
(repo root, visible — like `Cargo.toml`), generated content lives in
`.stitch/state.toml` (hidden, tool-owned). The tool never rewrites the
authored file after `init`.

## End state

```
~/dots/
  stitch.toml            # authored: vars, when, hooks, ignore. Read-only to the tool.
  .stitch/
    state.toml           # generated: target, files, patterns. Tool-owned.
    hooks/               # unchanged
    secrets.enc          # v0.4, unchanged
```

| Field | File | Kind |
|---|---|---|
| `vars` | `stitch.toml` | user variables |
| `when` | `stitch.toml` | behavior |
| `hooks` | `stitch.toml` | behavior |
| `ignore` | `stitch.toml` | behavior |
| `target` | `state.toml` | inventory |
| `files` | `state.toml` | inventory |
| `patterns` | `state.toml` | inventory |

Fields do not overlap across files, so the merge has no conflict resolution —
authored fields come solely from `stitch.toml`, inventory solely from
`state.toml`.

## 1. Split serde types + load-time merge

**Problem:** `config.rs` has one `Config`/`Store`/`TargetEntry` hierarchy
(`config.rs:7-58`) parsed from and serialized to one file. `Config::load`
reads `.stitch/config.toml` (`config.rs:77`); `Config::save` writes it
(`config.rs:93`).

**What to change:**

Introduce two serde structs mirroring the field-ownership table, plus a merged
view used everywhere downstream:

```rust
// Authored — from stitch.toml. Read-only after init.
pub struct AuthoredConfig {
    pub vars: HashMap<String, String>,
    pub stores: BTreeMap<String, AuthoredStore>,
}
pub struct AuthoredStore {
    pub ignore: Vec<String>,
    pub when: WhenClause,
    pub hooks: Hooks,
    pub targets: BTreeMap<String, AuthoredTarget>, // keyed by name
}
pub struct AuthoredTarget {
    pub ignore: Vec<String>,
    pub when: WhenClause,
}

// Generated — from .stitch/state.toml. Tool-owned.
pub struct GeneratedState {
    pub stores: BTreeMap<String, GeneratedStore>,
}
pub struct GeneratedStore {
    pub target: Option<String>,
    pub files: Vec<String>,
    pub patterns: Vec<String>,
    pub targets: BTreeMap<String, GeneratedTarget>, // keyed by name
}
pub struct GeneratedTarget {
    pub target: String,
    pub files: Vec<String>,
    pub patterns: Vec<String>,
}

// Merged view — built at load, never serialized as one unit. `Config` keeps
// its name and method surface (`.stores`, `.vars`, `.validate()`, `.empty()`
// for tests) so apply/status/doctor and fragment validation are unchanged.
// Only the field *types* change: `HashMap`→`BTreeMap`, `Vec<TargetEntry>`→
// name-keyed map. `vars` is carried over from the authored half.
pub struct Config {
    pub vars: BTreeMap<String, String>,          // from authored
    pub stores: BTreeMap<String, Store>,
}
pub struct Store {           // same shape as today, minus serialization
    pub target: Option<String>,
    pub files: Vec<String>,
    pub patterns: Vec<String>,
    pub ignore: Vec<String>,
    pub when: WhenClause,
    pub hooks: Hooks,
    pub targets: BTreeMap<String, TargetEntry>,  // keyed by name (item 3)
}
```

`BTreeMap` everywhere, not `HashMap` — deterministic ordering for stable diffs
(see item 6).

New `Config::load(repo_root)`:
1. If `stitch.toml` missing and `.stitch/config.toml` present → return the v0.2
   error from item 5. Do not parse the old file.
2. Parse `stitch.toml` → `AuthoredConfig` (missing file = empty authored).
3. Parse `.stitch/state.toml` → `GeneratedState` (missing file = empty state;
   `init` has not run, or a store has behavior but no links yet).
4. Merge (algorithm below).
5. Validate the merged result (`validate()` unchanged — operates on the view).

Merge:
```
config.vars = authored.vars            // top-level vars live only in authored

for name in union(authored.stores, generated.stores):
  a = authored.stores.get(name)
  g = generated.stores.get(name)
  store.target   = g.and_then(target)
  store.files    = g.files or []
  store.patterns = g.patterns or []
  store.ignore   = a.ignore or []
  store.when     = a.when or default
  store.hooks    = a.hooks or default
  store.targets  = merge_targets(a.targets, g.targets, warnings)  // below
```

`merge_targets(authored, generated, warnings)` — name is the join key; an
entry appears in the merged map iff it has a **generated** half (authored-only
targets are skipped, not constructed — see below). Per-name:
```
for tname in union(authored, generated):
  a = authored.get(tname)   // Option<AuthoredTarget>: when, ignore
  g = generated.get(tname)  // Option<GeneratedTarget>: target, files, patterns
  let Some(g) = g else {
    // authored-only target: behavior declared, no link inventory.
    warnings.push(format!("store '<s>' target '{tname}': behavior in \
        stitch.toml but no target in state.toml (orphaned after rename?)"));
    continue;   // skip — contributes no link
  };
  merged.targets[tname] = TargetEntry {
    target:   g.target,
    files:    g.files,
    patterns: g.patterns,
    ignore:   a.map_or([], |a| a.ignore),
    when:     a.map_or(default, |a| a.when),
  }
```
- **Generated-only target** (name in `state.toml`, not in `stitch.toml`): legal
  — default `when` (always), default `ignore`. `doctor` flags it as dead-ish
  the same way it flags a generated-only store (item 7).
- **Authored-only target** (name in `stitch.toml`, not in `state.toml`): the
  cross-file analogue of an orphaned-behavior store — behavior declared but no
  link inventory. It is **not** a load error: a `TargetEntry` structurally needs
  a `target`, but a missing one just means that target contributes no link.
  Per SPEC.md:62 ("stitch.toml only … `doctor` warns") and SPEC.md:86
  ("Renaming in one file without the other orphans the entry; `doctor` warns"),
  this case is **load-OK + skip**: the entry is dropped from the merged view
  (no link to create) and appended to `loaded.warnings`. `doctor` surfaces it
  under its orphaned-behavior check (item 7). This keeps the per-target
  treatment symmetric with the store-level treatment (both: load OK, doctor
  warns) and avoids one stray target entry taking down `status`/`apply` on
  unrelated stores. **SPEC.md:62/86 already match this — no SPEC change needed.**

`is_multi_target()` (`config.rs:64`) becomes `!store.targets.is_empty()` —
unchanged semantics, now keyed by name.

`Config::save` is **removed**. Replaced by `GeneratedState::save` writing
only `.stitch/state.toml` (same temp-file + rename atomicity, `config.rs:99-118`).
Nothing serializes `stitch.toml` after `init`.

**Load return type (resolved).** The merged `Store` view is read-only: it is
built at load and never serialized. But writers need to mutate the *generated*
half only. So `load` returns both halves alongside the merged view, not a
single merged struct:

```rust
pub struct Loaded {
    pub authored: AuthoredConfig,   // read-only to callers; never saved
    pub generated: GeneratedState,  // writers mutate this, then .save()
    pub config: Config,             // merged view for reads (apply/status/doctor/hooks); carries `vars`
    pub warnings: Vec<String>,      // non-fatal load-time notices (item 5 stale-config)
}

impl Config {
    /// Load authored + generated, return both halves and the merged view.
    /// `stitch.toml` missing + `.stitch/config.toml` present → v0.2 error (item 5).
    pub fn load(repo_root: &Path) -> Result<Loaded, ConfigError> { ... }
}
```

There is exactly one load path: `Config::load`. It returns `Loaded`, which
holds the generated half in place for writers to mutate. There is **no**
separate `GeneratedState::load` — item 2's prose that implied one is updated
to read from `Loaded.generated` instead.

Writer pattern (replaces every `let mut config = Config::load; config.stores.insert; config.save`):

```rust
let mut loaded = Config::load(&root)?;
// reads use the merged view as today (borrow site takes &Config):
let target = loaded.config.stores.get(name).and_then(|s| s.target.as_deref())...;
let statuses = store::status_all(&root, &loaded.config, &platform);
// write touches only the generated half:
loaded.generated.stores.entry(name.into()).or_default().target = Some(...);
loaded.generated.save(&root)?;
```

**`add`/`adopt` preview path (special case — read carefully).** The simple
"mutate generated then derive" pattern above doesn't cover the *pre-commit*
preview: `add`/`adopt` call `store::apply_store(&root, name, &new_store, …)`
(`main.rs:401-410`, `main.rs:538-550`) to create the link **before** persisting,
and that takes `&Store` (the merged view). But the store doesn't exist in
`loaded.config` yet — it's being created. So add/adopt build **two literals**,
not one derived from the other:

```rust
// (1) a Store for the apply_store preview — default behavior (authored side
//     is empty for a brand-new store) + the new inventory:
let new_store = config::Store { target: Some(target_str.clone()), files, patterns,
    ignore: vec![], when: WhenClause::default(), hooks: Hooks::default(),
    targets: BTreeMap::new() };
store::apply_store(&root, name, &new_store, &platform, opts);   // preview/create
// (2) the same inventory as a GeneratedStore for persistence:
loaded.generated.stores.insert(name.into(), GeneratedStore {
    target: Some(target_str.clone()), files, patterns, targets: BTreeMap::new() });
loaded.generated.save(&root)?;
```

This mirrors v0.2's existing two-literal shape (`main.rs:375,523` already build
a `Store` literal for the preview); the only change is the second literal is a
`GeneratedStore` and the save targets `state.toml`. No re-merge helper needed.

`Config` (the merged view container) keeps its current method surface
(`config.stores`, `config.vars`, `validate()`, `empty()` for tests) — the only
delta from v0.2 is `HashMap`→`BTreeMap` and the name-keyed `targets` map.
Borrow sites that take `&Config` (`store::apply_all`, `status_all`,
`check_unknown_names`) are unchanged. `doctor` does **not** take `&Config`
anymore — see item 7. The `Loaded` wrapper is what commands hold; writers
mutate `loaded.generated` then call `loaded.generated.save()`.

**AGENTS.md alignment.** AGENTS.md currently says "`TargetEntry` gains a `name`
field." With name-keyed maps (item 3) the name *is* the key; a `name` field on
`TargetEntry` would be redundant and desync-prone. **Decision: name = map key,
no field on `TargetEntry`.** AGENTS.md is updated to match (see DoD).

**Files touched:** `src/config.rs` (rewrite), all callers of `Config::load` /
`config.stores.insert` / `config.save` (item 2).

**Unchanged (call out to avoid rework).** `find_root` (`config.rs:185`) and
`resolve_root` (`main.rs:77`) are unchanged: `init` still creates `.stitch/`,
so the repo-marker lookup keeps its current key. `expand_home`,
`is_safe_fragment`, `validate_fragments` are byte-unchanged. `validate`
(`config.rs:128`) is **logic-unchanged but mechanically touched**: its
`for te in &store.targets` (`config.rs:131`) iterates a `Vec` today and yields
`&TargetEntry`; with `targets: BTreeMap<String, TargetEntry>` it must become
`store.targets.values()` (yields `&TargetEntry`). Fragment-validation tests
are unchanged because they assert on error *messages*, which don't move. Same
mechanical `.values()` touch at the item-3 iteration sites (`store.rs:104`,
`store.rs:318`, `main.rs:277`) — item 3 already flags those, so this just
reconciles item 1's "Unchanged" wording with item 3.

**Test:** unit test that authored+generated halves merge to the expected
`Store`; test each half-missing case (authored-only store, generated-only
store, authored-only *target* → skipped + warning, generated-only target →
default behavior); test that `load` refuses a v0.2 layout.

## 2. Writers target `state.toml` only

**Problem:** `cmd_add` (`main.rs:581`), `cmd_adopt` (`main.rs:441`),
`cmd_remove` (`main.rs:620,632`) mutate `config.stores` and call
`config.save`, which writes the whole merged config back to one file. This is
the comment-clobbering path.

**What to change:**

- `init`: write an empty `stitch.toml` (with a header comment, e.g.
  `# stitch — authored config. Edit freely; the tool never rewrites this.`)
  and an empty `.stitch/state.toml`. Both via temp-file + rename.
- `add`/`adopt`: `Config::load` (the one load path) → hold the `Loaded`; mutate
  `loaded.generated.stores[name]` inventory fields; `loaded.generated.save()`.
  Never touch `stitch.toml`. The merged view in `loaded.config` (default
  behavior for a new store + the in-memory generated half) is what
  `apply_store` previews against.
- `remove`: from the `Loaded` returned by `Config::load`, drop the store's
  entry in `loaded.generated`, save. **Leave the `stitch.toml` behavior in
  place** — the tool does not rewrite authored config. `doctor` flags the
  orphaned behavior (item 7); the user removes it via `stitch edit` if they want.
- `edit`: open `stitch.toml`, not `.stitch/config.toml`.

The transactional boundaries in `adopt`/`add` (move file → create link →
write state) are unchanged — `state.toml` save is still the final atomic
step, and the rollback paths (`rollback_adopt_move`,
`discard_uncommitted_add`) are unaffected because they precede the save.

**Files touched:** `src/main.rs` (`cmd_init`, `cmd_add`, `cmd_adopt`,
`cmd_remove`, `cmd_edit`).

**Test:** integration test — add a store, confirm `stitch.toml` is byte-identical
to its post-`init` content (comments preserved) and `state.toml` gained the
entry. Same for `adopt`/`remove`.

## 3. Multi-target name keying

**Problem:** `targets` is `Vec<TargetEntry>` (`config.rs:27`), consumed as an
array in `store.rs:103-104,317-318` and `main.rs:275-277`. Two targets can
share a path (same `~/.config/helix` on different hostnames), so the path
cannot be the join key across the two files. v0.2 has no name field.

**What to change:**

`targets` becomes `BTreeMap<String, TargetEntry>` keyed by name in the merged
view; `AuthoredStore.targets` and `GeneratedStore.targets` are name-keyed
maps on their respective sides. The TOML shape (from SPEC §Config):

```toml
# stitch.toml
[stores.helix.targets.laptop]
when = { hostname = "laptop" }

# .stitch/state.toml
[stores.helix.targets.laptop]
target = "~/.config/helix"
```

Iteration sites (`store.rs:103`, `store.rs:317`, `main.rs:275`) iterate
`.values()` — order is now alphabetical by name, deterministic.

**Scope cut for this release (resolved).** v0.2 `add`/`adopt` only ever create
flat single-target stores (`main.rs:375,523` build `targets: vec![]`);
multi-target stores are hand-authored in `stitch.toml` today and stay so. And
`--name`/`-n` already means the **store** name (`cli.rs:60` adopt), so reusing
it for a *target* name would collide. **Decision: this cut only (a) keys
existing `targets` entries by name (the cross-file join key) and (b) generates
names inside `migrate`.** No new `add`/`adopt` CLI surface for target names —
`add`/`adopt` continue to produce flat `target`-field stores with no entry in
the `targets` map. The naming-generation algorithm below therefore applies
**only** to `migrate`. A future cut can add `--target-name` if CLI-created
multi-target stores are wanted.

**Files touched:** `src/config.rs` (struct shapes), `src/store.rs`
(apply/status consumers: `store.rs:104`, `store.rs:318` gain `.values()`),
`src/main.rs` (`cmd_list`). `cmd_add`/`cmd_adopt` don't build target *entries*
(per the scope cut), but their `Store` literals construct `targets: vec![]`
(`main.rs:386`, `main.rs:530`) which won't typecheck against
`BTreeMap<String, TargetEntry>` — a one-token mechanical change to
`targets: BTreeMap::new()` in each. (The add/adopt preview literal in item 1
already shows `targets: BTreeMap::new()`.)

**`cmd_list` output format (resolved).** `main.rs:275-279` currently prints each
target entry's path, so two targets sharing a path are indistinguishable. With
name keying, print `name → target`:

```
  helix (2 targets)
      laptop → ~/.config/helix
      server → ~/.config/helix
```

Single-target (flat `target` field) and no-target stores keep their current
format (`name → ~/.config/x`, `name (no target)`). The header count line stays.

**Test:** multi-target store applies to the right subset by hostname; two
targets sharing a path are distinguishable by name in output (see item's
`cmd_list` format below); migrate names multi-target entries per the
deterministic rule (golden file in item 4).

## 4. `stitch migrate` command

**Problem:** Existing v0.2 repos have a single `.stitch/config.toml`. They
need a one-shot, deterministic conversion.

**What to change:**

New `stitch migrate` subcommand. Algorithm:

1. Require `.stitch/config.toml` present and `stitch.toml` absent (else: "nothing
   to migrate" / "already migrated"). Refuse overwrite if `stitch.toml` exists.
2. Parse the v0.2 file into a frozen `LegacyConfig` serde type (see below) —
   **not** the post-split types, which no longer carry the v0.2 field layout
   (item 1 removes the old `Config`/`Store`/`TargetEntry` serde structs).
3. Split per the field-ownership table into `AuthoredConfig` + `GeneratedState`.
4. Name multi-target entries (algorithm below).
5. Write `stitch.toml` (with header comment) and `.stitch/state.toml` via
   temp-file + rename.
6. Remove `.stitch/config.toml` **last**, only after both writes succeed —
   so a crash leaves the original intact. Recommend `trash` over `rm` per
   AGENTS.md; migrate may use `std::fs::rename` to a `.bak` path instead of
   deletion, gated behind a flag. Default: trash/rename to
   `.stitch/config.toml.bak`.

`LegacyConfig` lives in `src/config.rs` **unconditionally** (parse-only, no
`save`). It is cheap to keep compiled, and leaving it in tree documents the v0.2
shape for anyone reading `migrate` later — a `#[cfg(feature)]` gate would force
a `Cargo.toml` feature entry and a conditional build for no real benefit. Its
fields mirror the current `Config`/`Store`/`TargetEntry` exactly
(`config.rs:7-41`):

```rust
/// Frozen v0.2 layout, used only by `migrate`. Never serialized.
#[derive(Debug, Deserialize)]
struct LegacyConfig {
    #[serde(default)]
    vars: HashMap<String, String>,
    #[serde(default)]
    stores: HashMap<String, LegacyStore>,
}
#[derive(Debug, Deserialize)]
struct LegacyStore { /* mirrors v0.2 Store: target, files, patterns, ignore, when, hooks, targets: Vec */ }
#[derive(Debug, Deserialize)]
struct LegacyTargetEntry { target, files, patterns, ignore, when }  // v0.2 array form, no name
```

**Comment preservation (decision — must be explicit).** `migrate` parses via
`toml::from_str` into `LegacyConfig` and writes the authored half via
`to_string_pretty`, which **drops comments** — the very harm the split exists
to end. This is inherent to a structural one-shot conversion: v0.2 comments
decorate a single-file layout that no longer exists, so there is no faithful
place to carry them into the split files. Rather than silently lose them,
`migrate` is **documented as comment-lossy** and the conversion prints
`note: comments in .stitch/config.toml are not carried into stitch.toml; the
original is preserved as .stitch/config.toml.bak` so the user can re-add them.
The original `.bak` is the recovery path. (Switching the authored-half write to
`toml_edit` would preserve formatting but not v0.2 comments either, since the
AST is being split across two files — so it buys little and adds a dependency.
`init` is unaffected: it writes a static string.) This trade-off is recorded
in SPEC §Migration and CHANGELOG so it is not a surprise.

Multi-target naming algorithm (deterministic):
```
seen = {}
for i, te in v2_targets (1-based):
  base = te.when.hostname.unwrap_or_else(|| format!("target-{i}"))
  // loop until unique: a hostname literally named "target-N" (or any repeat)
  // must not collide with a positional fallback.
  name = base.clone(); n = 1
  while seen.contains(&name) { name = format!("{base}-{n}"; n += 1) }
  seen.insert(name)
```
Hostname-first because it is meaningful to the user; positional fallback when
absent, and a suffix loop on collision so the result is always unique. (The
plain `target-{i}` fallback of the earlier draft could itself collide with a
hostname-derived name.) Single-target stores using the flat `target` field
(not `targets[]`) are unaffected — no name needed.

`--dry-run` prints the planned `stitch.toml` + `state.toml` without writing.

**Files touched:** `src/cli.rs` (subcommand), `src/main.rs` (`cmd_migrate`),
`src/config.rs` (v0.2 parse + split helper + naming algorithm). SPEC.md
§Migration note re: comment loss; CHANGELOG note.

**Test:** golden-file test — a representative v0.2 config (flat target,
multi-target with and without hostname, `when`/`hooks`/`ignore`, plus one
comment to anchor the lossy-behavior assertion) → assert the two output files
match expected content byte-for-byte. Assert the expected `stitch.toml`/`state.toml`
contain **no** comments (migrate is comment-lossy by design — see decision
above), and that stdout/stderr carries the comment-loss note. Assert
`.stitch/config.toml.bak` exists and equals the original (comments included).

## 5. Reject v0.2 `.stitch/config.toml`

**Problem:** Silent dual-format support defeats the authorship boundary. We
must not read the old file.

**What to change:**

In `Config::load`, before the new-format parse:
```
if !repo_root.join("stitch.toml").exists()
   && repo_root.join(".stitch/config.toml").exists():
  return Err("v0.2 config found at .stitch/config.toml — \
              run `stitch migrate` to split into stitch.toml + .stitch/state.toml")
```
If both exist (partial/aborted migrate), new format wins and emit a warning
that `.stitch/config.toml` is stale and can be removed.

**Warning channel (resolved).** `Config::load` returns `Result<Loaded, _>` with
no logging side channel today, and printing to stderr inside `load` is a
layering smell (it's a pure parse step called from every command, including
`status`). Thread the warning through the return instead: `Loaded` carries a
`warnings: Vec<String>` field (item 1's `Loaded` struct gains this), populated
during load. Each command prints `loaded.warnings` to stderr before proceeding —
a one-line addition at each call site (7 of them), no behavior change for the
common case. This keeps `load` pure and makes the stale-config warning
testable (assert on `loaded.warnings` rather than scraping stderr).

**Files touched:** `src/config.rs` (`Config::load`, `Loaded`), `src/main.rs`
(every `Config::load` call site — print warnings).

## 6. Deterministic `state.toml` ordering

**Problem:** `toml::to_string_pretty` over a `HashMap` serializes in
iteration order, which is randomized for `HashMap` per-process (verified
2026-06-17: identical map serialized as `alpha/mike/zebra` in one process and
`zebra/alpha/mike` in another). v0.2 state writes are therefore already
non-deterministic across `stitch` invocations — a latent git-diff noise bug
bundled into this cut for free.

**What to change:**

Use `BTreeMap` for all serialized map collections (item 1 already specifies
this). That fixes store/target key ordering, which is the dominant source of
diff noise (v0.2 stores/targets are `HashMap`/`Vec`).

But `files` and `patterns` are `Vec<String>` — deterministic within one process
(insertion order) but not across runs. `add` appending to an existing store, or
`migrate` preserving v0.2 array order, can produce a differently-ordered
`state.toml` across two `stitch` invocations. For stable git diffs, serialize
`files`/`patterns` **sorted** in `GeneratedState::save`, not in array order.
Cleanest: sort the `Vec`s in-place at the top of `save` before serializing
(`state.toml` is tool-owned, so imposing a canonical order is the tool's
prerogative and never destroys authored content). Verify the toml crate writes
a `BTreeMap`-backed intermediate in key order (it does). Note the signature
delta from v0.2: in-place sort makes `save` take `&mut self`, not the `&self`
of v0.2's `Config::save` (`config.rs:93`). All call sites already hold the
`GeneratedState` mutably (writers go through `loaded.generated`), so this is
internal — just don't copy the v0.2 `&self` shape.

**Files touched:** `src/config.rs` (struct field types + `GeneratedState::save`,
signature `&mut self`).

**Test:** add store A then B, snapshot `state.toml`; reset, add B then A,
snapshot; assert identical. Also: add a store with `--files c,a,b`, snapshot,
then re-`add`... re-save via any mutation, assert `files` is emitted as
`["a", "b", "c"]` (sorted), stable across runs.

## 7. `doctor`: orphan detection

**Problem:** With authored and generated now separable, two new failure modes
exist that `doctor` (`store.rs:doctor`) must surface:
- **Orphaned behavior** — store in `stitch.toml` with no `state.toml` entry
  (e.g. after `remove`, which deliberately leaves behavior behind).
- **Orphaned links** — symlinks pointing into the repo that no store
  references (the "files all over the place" problem from the design session:
  retargeting/deleting a store leaves the old link stranded). This is read-only
  detection only; removal is item 8.

**What to change:**

`doctor` gains two checks:
1. For each store name in `AuthoredConfig.stores` not in
   `GeneratedState.stores`: `[warn] store '<name>': behavior configured but no
   links (orphaned after remove?)`.
2. Scan default dirs (`~`, `~/.config`, `~/.local/share` — reuse the `import`
   scan dirs) for symlinks resolving into `repo_root`. For each, check whether
   any merged store's target set covers it. Uncovered →
   `[warn] orphan link: <path> → <resolved> (no store references it)`.

Check 2 reuses the scanner built for item 8; if 8 is deferred, ship check 1
alone and note check 2 as blocked-on-8.

**Signature change (must be explicit).** Check 1 compares
`AuthoredConfig.stores` against `GeneratedState.stores` directly — but the
merged `Config` (`store.rs:392`, called at `main.rs:668`) renders an
authored-only store indistinguishable from a both-files-but-empty-inventory
store (both merge to `target: None`). So `doctor` must take `&Loaded` (the two
halves), not `&Config`. `cmd_doctor` (`main.rs:666`) accordingly loads via
`Config::load` and passes `&loaded`, and check 2 still uses `loaded.config`
(the merged view) for the target-set membership scan.

**Files touched:** `src/store.rs` (`doctor` signature: `&Config` → `&Loaded`;
check-1 logic), `src/main.rs` (`cmd_doctor` call site), possibly a new
`src/scan.rs` shared with item 8.

**Test:** repo with a `remove`d store → orphaned-behavior warning; symlink
into repo not covered by any store → orphan-link warning (check 2, gated on
item 8's scanner).

## 8. `prune` + `import` (shared scanner)

**Problem:** The orphan-link detection in item 7 is read-only; users need a
way to act on it. `import` (already on the roadmap) is the inverse — scan
repo-pointing symlinks and add them to config. The two share a scanner and
should be built together.

**What to change:**

New `src/scan.rs`:
```rust
pub struct FoundLink {
    pub link: PathBuf,       // the symlink location
    pub resolves_to: PathBuf,// canonicalized, inside repo_root
}
pub fn scan_for_repo_links(
    repo_root: &Path,
    scan_dirs: &[PathBuf],
) -> Vec<FoundLink> { ... }
```
Walks each scan dir, follows symlinks, canonicalizes, keeps those whose target
`starts_with(repo_root)`. Reuses `linker::points_into_repo` logic (canonicalize
+ lexical normalize fallback) for the classification.

- `stitch import`: for each `FoundLink`, derive store name (from the repo-side
  path's top segment) and write a `state.toml` entry. `--dry-run` lists; prompt
  or `-y` to write.
- `stitch prune`: for each `FoundLink` not referenced by any merged store,
  remove the symlink (foreign symlinks are already excluded by
  `points_into_repo` — only repo-pointing links are candidates, and only those
  unreferenced are pruned). `--dry-run` lists; prompt or `-y` to remove.
  Removes only the symlink, never the repo content.

Both are non-destructive by default (consistent with the AGENTS.md red lines);
they list first and require confirmation.

**Files touched:** new `src/scan.rs`, `src/cli.rs` (two subcommands),
`src/main.rs` (`cmd_import`, `cmd_prune`), `src/store.rs` (doctor check 2
wired to the scanner).

**Test:** repo with a stranded symlink → `prune --dry-run` lists it, `prune`
removes only the link; repo with an unmanaged repo-pointing symlink → `import`
adds the `state.toml` entry and a subsequent `apply` is a no-op.

## Resolved decisions

1. **`ignore` placement.** SPEC puts `ignore` in `stitch.toml` (behavior). It
   could arguably be inventory-adjacent ("which files in this store to link").
   **Keep in `stitch.toml`** — it is a resolution rule, not a link target, and
   a user wants it version-controlled and commented. Revisit if users complain
   it belongs with the link list.
2. **`state.toml` header comment.** Since the tool reserializes it, any header
   is volatile. The `toml` crate does **not** round-trip comments —
   `to_string_pretty` drops them and `from_str` won't preserve them on the next
   save. So a header can only survive by injecting it as a raw prefix outside
   the TOML data model: **prepend** a fixed one-line header on write
   (post-serialize, pre-`write_all`), **strip** that exact known prefix on read
   (pre-`from_str`). The line:
   `# Generated by stitch — do not hand-edit; use stitch commands.`
   Strip matches the exact bytes (length-prefixed check, not a fragile regex);
   if the prefix is absent or differs, parse the file verbatim. Tested by a
   save→load roundtrip asserting the header is present and content survives.
3. **Does `edit` need a `--state` variant?** No — `state.toml` is tool-owned.
   If a power user wants to hand-edit inventory, they edit the file directly.
   Skip until requested.
